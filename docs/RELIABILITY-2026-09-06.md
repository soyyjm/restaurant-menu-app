# Menu 系统第一轮可靠性修改

状态：本地修改与回归验证完成，未发布；未写入线上数据库。

## 使用范围

系统仅供餐馆管理层内部使用。沿用现有登录方式，不新增员工账号、细分角色、权限层级或数据库授权规则。本地缓存按登录账号保存，仅用于避免切换账号时混用草稿，不代表引入新的业务权限模型。

## 本轮完成

- 每日菜单、菜库、删除及打印设置的云端写入检查返回错误；失败后保留待同步记录，并提供“Reintentar”。网络恢复后尝试补传。
- 本地使用单个 JSON 快照保存菜单、日期、价格、历史、设置和待同步记录，避免多项独立写入导致半份草稿。
- 重载页面时保护待同步数据，云端旧值不能直接覆盖它；同一页面的写入串行执行，新编辑到达时继续同步最新状态。
- 日期按 Europe/Madrid 计算。切换日期打开该日已存菜单；未使用日期打开空菜单。编辑非今日菜单时显示提示。
- 保存和恢复菜单价格。历史操作区分“复制到所选日期”和“恢复原日期及价格”。旧历史缺少价格时恢复操作提醒复核。
- 清空和删除菜品可使用“Deshacer”撤销；日期切换和历史替换也保留一步撤销。撤销仅在本次页面打开期间有效。
- 手机添加按钮换行，触屏上直接显示菜品编辑按钮。“Ambos”改为“Menú + biblioteca”。
- 编辑当天菜品默认不改菜库；勾选“Actualizar también la biblioteca”后才更新匹配的菜库记录。
- 翻译期间禁止重复添加，状态文字不进入菜名；输入改变后忽略过期结果；外部请求有超时。无法完成翻译时允许人工填写，不再逐词拼出貌似完成的译文。
- 套餐翻译失败不再把原文当作译文；成功结果先作为待审查草稿，不自动写入云端。复制套餐版本包含当前编辑字段，并深复制编辑对象。
- 登录回调不再直接等待 Supabase API；切换账号停止后续旧会话写入，清除当前套餐界面缓存。未登录草稿可以在设置中明确选择恢复。
- 直接打印的弹窗被拦截时给出提示，不再直接访问空窗口对象。

## 数据兼容

不新增表或列，不执行 SQL 脚本。

云端 `selected_menu.dishes` 和 `menu_history.dishes` 仍只包含 `primer`、`segundo`、`postre` 三个数组。日期、价格、历史价格和特殊价格放在现有 `settings.print_settings.menu_state_v1` 下。旧菜品 JSON 保持可读取。

本地缓存改用 `menu_v3_<account>_snapshot`，旧 `v2_*` 缓存保留。旧缓存只迁入第一次使用的新缓存身份，避免再次登录另一个账号时重复继承旧内容。

菜单、历史和设置仍是多次云端写入，不是数据库事务。任一步失败都保留待同步状态，重试采用相同键覆盖；不把部分成功报告为全部成功。

## 验证

运行：

```sh
node --test tests/menu-reliability.test.cjs
```

16 项回归测试通过：马德里午夜、失败保存与重试、断网重载、多日期待同步、清空与撤销、历史复制/恢复、账号缓存分离、翻译竞态、套餐翻译失败、本地存储失败、连续编辑写入、新设备恢复价格、部分表写入失败、删除重试、输入价格未失焦时保存、会话变化、日期切换（部分测试覆盖多个场景）。

本地 Chromium 浏览器使用模拟菜品验证：

- 320、390、768、1440px 下日期、价格及三个添加按钮均在屏幕内。
- 添加菜单与菜库，修改价格后重载，菜品与价格保留。
- 修改当天菜品时未勾选同步菜库，原菜库名称保留。
- 清空后撤销，菜品与价格恢复。
- 浏览器检查期间未发现控制台 error。

浏览器检查拦截了 Supabase 网络请求，没有使用真实账号或写入正式数据。界面截图保存在 `output/playwright/`。

## 发布前验证及后续工作

本轮未修改部署配置，也没有发布。

发布前应确认实际托管目标，并用管理层账号验证真实保存、第二设备读取、权限拒绝后的错误提示和打印。所有管理设备应刷新到同一版本：旧页面保存打印设置时不会保留新增的菜单元数据。

第一轮结束时的后续建议包括：套餐多语言按稳定菜品 ID 关联、套餐草稿持久恢复、常用菜与批量录入、统一 PDF/预览模板、导入导出备份、服务端翻译接口、线上 RLS 核实。前三项已在[第二轮](WORKFLOWS-2026-09-06.md)本地完成，验证结果与剩余边界见该文档。

本轮不解决多设备同时编辑同一菜单的冲突；仍可能以后完成的写入覆盖先前写入。数据库的现有 singleton/owner 设计保持不变，不能据本轮改动认定多个独立管理账号已具备共享餐厅数据的正确权限。
